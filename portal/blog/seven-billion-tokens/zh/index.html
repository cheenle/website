这篇文章从一张账单开始。不是因为账单好看 —— 它九成五是缓存重读 —— 而是因为在这整个故事里，账单是唯一一件不会跟你争辩的东西。其余所有论断，包括这张账单本身，都要拿去和别的什么对一次。

卷一

格物 · Investigating Things

到现场去问那个东西。五节讲会话库、测试运行与电台各自实际说了什么，以及两种「不去看」的失败方式。

先摆台账，再讲道理

2026-06-16 到 2026-09-05 之间，七个不同的 agent harness 在这个网站背后的那些仓库上跑过。我把这台机器上的每一处会话存储都解析了一遍 —— 约 2.7 GB 的 JSONL，外加四个 SQLite 库 —— 把每个工具自己记录的东西加了总。

事实

这七十亿 token 里有 95.2% 是重读。agent 并没有产出七十亿 token 的文字；它们是在每一次动手之前，把同一份契约重新加载一遍，一遍又一遍 —— 而真正的产出是 30,061,161 个 token。

声明：已记录 token 总量及其缓存重读占比。来源工件：表中列出的七处会话存储。版本／提交：普查 2026-09-05，工作树位于 mrrc_ft710@9c353a1、mrrc_modern@9d5f239、ft8 与 website 的 HEAD。环境：macOS arm64，仅本机会话存储。验证方法：按行过滤后解析 JSON，另加 SQLite 查询；Codex 与其自带的 threads.tokens_used 交叉核对。结果：7,007,437,567 tokens / 41,257 轮 / 882 会话。局限：只覆盖这台机器留存下来的部分；有三个工具完全不记 token（见「下限」一节）。日期：2026-09-05。

这个比例不是需要辩解的浪费。它是一个具体决定的代价：契约在 agent 每次动手之前都被加载，而不是一份没人打开的文档。卷三会回到这个决定买到了什么。

为什么七十亿只是下限，不是总数

这张表底下压着四处缺口，每一处都只有在你去找「工具没记下什么」的时候才会显形。

iFlow 什么都没记。它的存储里有 195 份会话、63,602 条记录，跨度 2025-10-20 到 2026-04-16，其中 37,202 轮 assistant 分布在六个模型后端上。每一轮都带着一个 usage 对象。每一个 usage 对象都写着 input_tokens: 0, output_tokens: 0。字段建好了，从来没填过。

所以对 iFlow 我只能估：843,290,639 个字符的会话文本，按每 token 约 3.6 字符算，约 234,247,399 个 token，合理区间 1.87 亿到 2.81 亿。这个数字是估算，任何工具都未记录它，并且被刻意排除在上面那个 7,007,437,567 的总量之外。

Hermes 记了结构，没记用量。它的 state.db 有一个 messages.token_count 列，9,121 行全是 0。但它记下的东西比 token 有意思得多：292 个会话、4,336 次工具调用，以及一个 source 字段把它们分成 cron 201 个、cli 68 个、weixin 23 个。277 份会话文件全部指向同一个 base_url。也就是说，有三个月时间，一个 agent 是被定时任务驱动的，还能从聊天软件里被唤起 —— 而没人测过它花了多少。

推论

那 201 个 cron 会话是整张台账里最要命的未测量项。定时的自主执行，恰恰是成本与影响范围同时不再被「一个人坐在键盘前」所约束的地方。而它同时是仪表最少的地方，这不是巧合：仪表跟着你害怕的东西走，而人们害怕的是交互式会话。

两处存储是空的或者是派生的。Cursor 的 ai-code-tracking.db 有六张表，五张零行。而 Qoder —— Cursor 的派生版 —— 那 588 个聊天气泡的 key 全部也在 Cursor 的存储里，Qoder 独有的是零个。两边都算就会把 1,500,804 个 token 重复计一次。Qoder 贡献为零，已排除。

留存期把开头截掉了。Claude Code 留存下来最早的会话是 2026-08-05。MRRC 仓库的第一个提交是 2026-03-06。那个产品族有五个月的工作，存储里就是没有了。

把 iFlow 的估算加进已记录总量，得到约 7,241,684,966 个 token、87,580 次交互、1,359 个会话 —— 而即便这个数字也仍然是下限，因为 Hermes 只贡献交互次数，一个 token 都没有。

主张

一个说不出自己漏了什么的测量，不是测量，是一个加了千分位逗号的感觉。有用的做法不是给出一个大数，而是保留两栏 —— 已记录与估算 —— 并且拒绝让它们合并。

我给出的第一个数字错了 16 亿

这次普查我跑了两遍。第一遍报出 5,380,941,148 个 token —— 那是一个未经核对的估算值，而且同时错在两个方向上。它错的方式，是这篇文章里最有用的东西。

它少数了，因为我只去找我以为 agent 工具会在的地方：~/.claude、~/.codex、~/.kimi-code、~/.iflow。而 Pi（16.3 亿）、MuleRun（4.716 亿）、Cursor（2710 万）和 opencode（419 万）分别在 ~/.pi、~/.mulerun、~/Library/Application Support/ 和 ~/.local/share/ 里。我没有把问题列全 ——「这台机器把 agent 会话存在哪些地方」—— 我只列了四个我已经知道的答案。

它又多数了，因为我把 usage 字段直接相加，却没问它们各自是什么意思。两处独立的错误，同一个形状：

  • Codex 报 input_tokens、output_tokens 和 cached_input_tokens。我把三个都加了。但 cached_input_tokens 是 input_tokens 的子集，不是兄弟 —— 某个会话显示 input 21,463、cached 3,456、output 485、total 21,948，而 21,463 + 485 正好等于 21,948。我把 Codex 虚增了 511,938,498。
  • Pi 报 input、output、cacheRead、cacheWrite、reasoning —— 还报一个 totalTokens，而它已经等于前四项之和。我把六个字段全加了。我把 Pi 虚增了大约它自身的全部。

线索一直摆在明面上。Codex 自己的 SQLite 库里有一列 threads.tokens_used，加总是 546,858,767。我的 JSONL 解析给出 1,058,625,328。我当时注意到这两个数「互相佐证」然后就放过去了 —— 因为 5.47 亿大约是 10.6 亿的一半，而我已经决定了答案是什么。

事实

校正后的 Codex 数字：会话文件解析得 547,796,667，数据库得 546,858,767 —— 相差 0.17%，可由 rollout 文件被单独归档的那部分解释。第一遍的 1,058,625,328 高出了 93%。

「致知在格物」这句出自《大学》的话，把神秘色彩剥掉之后讲的就是这件事。知识不是从字段名上掉下来的。它来自走到那个东西跟前去：把记录打开，验算 21,463 + 485 是不是等于 21,948，然后注意到它确实等于。

主张

一个从未与第二个独立产生的数字对过账的数字，还不是数字，它是一个关于数字的假设。纪律不是「小心点」，而是「找到另一个来源，并且把不一致当成信息，而不是当成噪声」。

本站的工程机制卷列了六种「看起来像速度的失败模式」。其中三种正是这个错误换了衣服：文档替代验证、测试数替代证据、AI 生成替代评审。三种都会产出一个自信的工件。一种都不会产出一个被核对过的工件。

一个业务诉求：一根你本来就插着的线

把台账拿开，这一切的起点要平常得多。

Yaesu FT-710 是一台 HF/50 MHz 电台。要远程操作它 —— 真音频、真频谱、真发射控制 —— 厂商给的答案是一个叫 SCU-LAN10 的专有配件。它要花钱，它多一个盒子，它是你和你自己电台之间又一个会坏的东西。

那个诉求比「做一个远程控制产品」窄得多。它是：这件事能不能只用那根已经插在电台背后的 USB 线做完？

这个问题就是智能体工程总纲页所说的 Echo 阶段 —— 在设计任何东西之前，先观察真实的电台和真实的操作者。而这次观察产出了两条决定下游一切的事实：

  • FT-710 的 USB 接口暴露出一座 FT4222 SPI 桥，能取出真正的频谱数据 —— 约 21 fps 的真实瀑布图，不是合成的 S 表回退值。
  • 同一根线承载 48 kHz 双向 Opus 音频与完整 CAT 控制。不需要 Hamlib，不需要 dongle，不需要第二台设备。

注意这是哪一类论断。它不是「我们想要一个产品」。它是「台子上这个东西具有这条性质，而我们是这样发现的」。FT4222 桥没有文档；它是看出来的。卷二讲的全部机器，就是为了不把「看」出来的东西弄丢。

事实

FT-710 这一族达到 439 项自动化测试，2026-09-05 实跑验证：Ran 439 tests in 10.675s / OK。其源码基线是 v1.8.1，已打包的 Windows 安装器是 v1.8.0 —— 两个不同的数字都对，因为它们说的是两个不同的工件。

声明：FT-710 测试数与版本拆分。来源工件：mrrc_ft710/tests/，经 venv/bin/python -m unittest discover -s tests；mrrc_ft710/CHANGELOG.md；mrrc_ft710/SDD/README.md；git tag 列表。版本／提交：HEAD 9c353a1，最新 tag v1.8.0，CHANGELOG 条目 [v1.8.1] — 2026-08-16。环境：macOS arm64，未接电台（按约束，测试与硬件无关）。验证方法：执行测试套；阅读 CHANGELOG、SDD README 与 tag 列表。结果：439 通过，0 失败。局限：自动化覆盖不等于实机验收；Windows 安装器比源码基线落后一个补丁。日期：2026-09-05。

对照组：没有 harness 的那六个月

这一段是让后文变得可测量的部分。在这套机器存在之前，我用大约六个月时间做过同一类工作，一样东西都没有。

iFlow 的存储覆盖 2025-10-20 到 2026-04-16：185 个会话、37,202 轮 assistant、六个模型后端 —— glm-5（17,925 轮）、qwen3-coder-plus（6,706）、kimi-k2.5（6,500）、minimax-m2.5（4,315）、glm-4.7（1,080）、iFlow-ROME-30BA3B（673）。项目包括：对着一个 Mac 控制应用打了 15,674 轮，对着最早的 MRRC 树打了 13,219 轮，PSK Reporter 分析器 3,193 轮，另外还有 FT8 解码器、CW 解码器、天线切换器、一个 Wi-Fi 重连脚本和一个 VPN 助手。

这不是小工作量，其中很多是有用的。PSK Reporter 那部分后来成了一篇公开的工作流文章。MRRC 那棵树后来成了一个产品族。但那里面没有任何 AGENTS.md，没有纳入版本控制的设计文档，没有机器可读的约束，没有任何形式的门禁。会话结束的时候，它学到的东西跟着一起结束了。

类比

王阳明曾试着去格亭前竹子 —— 格竹 —— 靠坐着沉思，七天之后病倒，关于竹子一无所获。这个故事通常被当成对他的批评来讲，但关键细节是方法：他把极大的诚意用在了一个没有反馈通路的程序上。三万七千轮、六个模型后端、零约束注册表、零设计契约，是同一个形状。努力是真的。程序收敛不了。

出处：格竹一事见《传习录》。此处作为关于方法的类比引用，不是关于竹子生物学的历史论断，也不是主张任何古典文本预见了 agent 工具。

按机制卷里的成熟度阶梯，那段时间是第 1 级走向第 2 级：Ad hoc，知识存在于个人动作与临时笔记里，正在朝可重复移动 —— 也就是已经有了基本的执行路径。它从未到第 3 级可追溯，因为没有任何东西把规格、测试、发布和证据连在一起。

真正要紧的对比不是「以前差，现在好」。而是同一个人、同一批电台、同样的业务问题，在有了让产出可以落地的地方之后，产出了另一种东西。卷二讲的就是那个地方。

卷二

致知 · Extending Knowledge

物格而后知至。三节讲一次观测如何变成机器能读的契约，以及 52 条这样的契约如何长成一个本体。

那套机器：约束在外，执行在内

取代「对着竹子枯坐」的东西，完整描述在工程机制页。短版本是一个两层的 harness。

外层是三组约束。业务 harness 固定这项工作为何存在、服务谁、什么算成功。技术 harness 固定领域模型、接口、安全不变量与恢复行为。产品 harness 固定交付物、验收标准、版本与发布状态、已知问题，以及哪些资产可复用。

内层是一个执行环境：人与 AI agent、带设计文档的仓库、工具与诊断、测试与评审、部署、现场遥测。边界规则才是要紧的部分 —— harness 必须让失败可见。工具输出保持可追溯到代码与环境。自动化测试不替代台架或现场验证。人与 agent 走同一套评审、证据与安全门禁。

两个环在这套 harness 里嵌套运行，而不是先后运行。外环是总纲页从前沿部署工程继承下来的交付环：Echo → Delta → Product。Echo 观察现场实相。Delta 用一个能跑的纵向切片证明风险最高的那条假设。Product 把结果稳定成可运营的东西 —— 而那恰恰就是之后可以交给 agent 的那个对象。内环是 Specify → Implement → Test → Review → Deploy / Observe → Update SDD，它在外环的每一个阶段内部跑很多遍。

事实

内环 —— Specify、Implement、Test、Review、Observe、Update SDD —— 是由 agent 用真工具、真仓库、真门禁执行的部分。意图、架构边界，以及「现有证据够不够说这件事已完成／已发布／已安全」的判断，留给一个具名的人。这是问责的分工，不是任务大小的分工。

让两个环耦合起来的是设计文档。它携带八个显式生命周期状态 —— planned、implemented、tested、bench-verified、field-verified、released、deferred、known-issue —— 状态之间的升级从不自动发生。每一条关于状态的声明都带一份最小证据记录：

最小证据记录
Claim · Source artifact · Version / commit · Environment
Verification method · Result · Limitations · Date

缺了这些字段，一个状态标签就是没有溯源的主张。本文每一个 .prov 块都是这个模板填满的样子 —— 它要么是这一页最乏味的特性，要么就是全部要点，取决于你有没有在六周之后被迫重建过一个数字到底是什么意思。

一条链，端到端，你能自己跑

抽象的机器描述起来很便宜。这里是整套系统唯一主张的那件事，在一次真实事故上的演示，附上你会敲的那条命令。

事故。在 Yaesu FT-710 上，CAT 命令 DN; 不是查询 DNR 降噪等级。它把当前 VFO 往下步进约 20 Hz，每调一次。一个每两秒读它一次的轮询循环 —— 如果你信命令手册，这是完全合理的一段代码 —— 会在操作者正在通话的时候，让一台在用的电台频率漂走。这件事真的发生过，发生在空中，并且被记在设计文档的版本史里，V1.2。

裁决。这次事故成了架构决策 AD-014：DNR 等级刻意不轮询。一条决策，写下来，写在拥有决策权的那份文档里。

约束。裁决成了一条机器可读规则，在 .agents/skills/sdd-guardian/harness/constraints.json 里：

constraints.json —— 本仓库 17 条规则之一
{
  "id":       "cat-no-dn",
  "severity": "block",
  "sdd_ref":  "AD-014; SDD V1.2 freq-drift incident",
  "scope":    [...],  "patterns": [...]
}

执行。install_hooks.py 注册两个 hook：SessionStart → prime，会话开启时加载约束摘要；以及 PreToolUse(Edit|Write) → hook，在一次编辑落盘之前检查它。这就是编辑前门禁。当 agent 试图把这个 bug 放回去时，发生的是：

2026-09-02 复现，2026-09-05 对 HEAD 重新验证
$ python3 .agents/skills/sdd-guardian/harness/sdd_context.py check probe_b4_tmp.py
SDD-GUARDIAN: blocking violations found:
[BLOCK] cat-no-dn (AD-014; SDD V1.2 freq-drift incident) probe_b4_tmp.py:2: return c.query("DN;")
    → On the FT-710, 'DN;' is NOT a DNR query — it steps the active VFO DOWN ~20 Hz per call. Polling it caused a live frequency-drift incident (V1.2). DNR level is intentionally not polled.
$ echo $?
2

退出码 2 就是一次被拦下的编辑长什么样。不是某人周一才去读的日志里的一条警告。这次编辑不会发生。

事实

一次现场事故成了一条设计文档裁决；裁决成了一条机器可读约束；这条约束拦住了 agent 把这个事故重新引入，退出状态非零。这条链上每一环都是仓库里的一个工件，而最后一环可以通过运行一条命令复现。

这就是物格而后知至，只是多了一件古典那句话里没有的事：到来的那个知识没有停在脑子里，也没有停在文档里。它进了一道门禁。被格的那个物是电台；到来的那个知，就是这条约束 —— 而且它仍在到来，每一次有人伸手去够 DN; 的时候。

有一个设计细节让整件事耐用：harness/index.json 把文件与主题路由到指向设计文档的类型化引用，但它不存内容。brief 与 sdd 命令在查询时实时切取 SDD/*.md。这个路由索引不会相对它所指向的文档变陈旧，因为它从来没持有过副本。

推论

大多数知识管理系统死于缓存。它们把权威文本复制到一个方便的地方，然后那份副本活得比原文的下一次修改更久。存引用、实时切取，更慢也更不方便，而它是唯一一个能扛住「文档一直在变」这件事的版本。

积累：52 条规则、三个仓库、一个本体

一次被拦下的编辑是轶事。这是积累的形状。

三个仓库里共有 52 条机器可读约束：mrrc_ft710 里 17 条（block 8、warn 4、info 5），mrrc_modern 里 21 条（8、6、7），mrrc_ft8 里 14 条（9、1、4）。普查 2026-09-02，2026-09-05 重新核对。每条都带 severity、一个指回架构决策或真实事故的 sdd_ref、一个 scope glob 和 patterns。

git 历史把谱系写得很直白。mrrc_modern 与 mrrc_ft710 共享同一个初始提交 —— 9403e2e，"Initial commit: FT-710 radio control server"。它不是受前者启发；它是从前者下来的。变的是那些单机型假设被抽成了 RadioBackend 接口和 RadioCapabilities 协商，于是一个纵向切片变成了覆盖三个电台 Profile 的平台。

而到了第三族，这套机器不再是后补的。mrrc_ft8 的第一个提交 —— d4a7a32，"headless FT8/FT4 server — DSP worker, TX path, CQ loop, Band Activity UI" —— 同时引入了 AGENTS.md、设计文档和 guardian skill。门禁随项目一起出厂，而不是三周后被螺栓拧上去，而在 mrrc_ft710 那边正是后者（初始提交 2026-07-06，guardian skill 2026-07-20）。

这些规则一直是从事故里长出来的，不是从政策里长出来的。提交 2bc3d30 写的是："docs: SDD V2.23 — record issues I8-I11, expand sdd-guardian harness to 21 rules"。四个新被理解的问题，注册表随之长到 21 条。

类比

朱熹在《大学章句》补传里的教法是今日格一物、明日格一物，直到积习既多，然后脱然自有豁然贯通处，一旦贯通则全体大明。总纲页上那个领域本体，构建顺序与本体通常的造法正好相反：重复出现的概念与约束，是只在同一份证据跨越产品边界反复出现之后，才被固化的。先 17 条规则，再 21 条，再 14 条 —— 然后，且不早于那时，才有了一套共享词汇：Control Lease、CommandIntent、Actuation、Observation、StateReport。

这个顺序不是审美偏好。先写出来的本体，是一个关于「这个领域里有什么」的猜测。而在三个产品族各自独立产出同一个区分之后写出来的本体，是对某件被证明为真的事情的记录。

推论

这里可复用的资产不是代码。是约束注册表本身，加上那个路由索引，再加上「把一次事故写成一条带 severity 和引用的规则」这个习惯。代码在不同电台之间的复用是有限的；而把一次现场意外变成一道永久门禁的那套机器，可以迁移到任何会有意外的领域。

卷三

知行合一 · Unity of Knowing and Acting

知而不行，只是未知。四节讲发布、讲漂移如何证明知识会停止成为知识，以及一个人仍然要签什么。

交付：发布了什么，以及持续发布要付什么

测试套是跑出来的，不是读出来的，2026-09-05：

三套测试均在 macOS arm64 上执行，未接电台硬件。设计上与硬件无关：测试在串口与音频边界处打桩。
产品族命令结果
FT-710venv/bin/python -m unittest discover -s testsRan 439 tests · OK
Modernvenv/bin/python -m unittest discover -s testsRan 682 tests · FAILED (errors=1)
FT8venv/bin/python -m pytest tests -q --collect-only937 tests collected

两条诚实的限定。Modern 那个 error 是 unittest.loader._FailedTest.test_macos_launcher —— 一个 Windows 专用启动器测试，在 macOS 上无法导入。它是环境局限，不是产品缺陷，而且它是 682 里面的一个，不是 682 之外的一个。而 FT8 那个数字是收集数，不是通过数：collected 统计的是 pytest 找到了什么，与一次绿色运行不是同一个论断。把 937 印出去而不带那个词，就是这篇文章一直在抓的那个错误。

交付本身毫不起眼，但承重。每个站点通过自己的脚本部署：校验必需文件存在、打包、经 SSH 备份线上站点、拷贝、解包、设置属主、重载 nginx。这些脚本里有四条规则，每一条都是用一次真实故障换来的：

  • 远端 heredoc 必须加引号（<<'REMOTE'），变量通过 ssh 命令行传入。不加引号的 heredoc 让本地 shell 先展开了 $(...)，这曾经使一个部署脚本在每一次运行时都静默跳过自己的备份 —— 同时照样打印出一个并不存在的备份路径。
  • tar -x 从不删除。把一个文件从包里排除掉，并不会移除早先某次运行已经发布出去的副本。要退役构建期工具就必须显式远端删除，因为文档根目录是全局可读的。
  • 备份按站、精简、轮转。绝不整站复制：服务端管理的二进制目录每个约 120–140 MB，而这就是一个临时卷如何涨到 3.7 GB 的 —— 1.7 GB 来自某站 13 份副本，2.0 GB 来自另一站 18 份副本 —— 而那块盘曾经满到过 100%。
  • 回滚提示只允许还原某一个站自己的目录。有三个脚本曾经打印一条删除整个文档根、再把单个子站还原进去的命令。在共享根目录上，那不是回滚，那是多绕了几步的一次停机。
事实

这四条规则各自对应一个发生过、被诊断过、并被写进部署脚本与工作区说明的缺陷。它们不是从清单上采纳的最佳实践；它们是带着理由的疤。

漂移：台账自己也会过时

跑测试套翻出来的东西比数字本身有意思。它翻出了四种不同的漂移，外加一个我自己提议的修正差点也漂了的案例。

① 落地页已经几周没更新了。它给 FT-710 挂着 V1.0 · 180+ tests→v1.8.1 · 439 tests，给 Modern 挂着 v1.10.1 · 593 tests→v1.12.1 · 682 tests，给 FT8 那一族挂着 40 tests→937 collected。两个都是靠跑测试套验证的，不是靠读任何文档。

② 证据台账落后了一个补丁。台账本应是跨项目可比数字的唯一来源，而它确实是 —— 这恰恰是它自己过时更要紧的原因。它写着 v1.12.0 · 633 tests→v1.12.1 · 682 tests。三天的工作把版本推进了一位、加了四十九项测试，而没有任何东西告诉台账。

③ 每一个约束注册表都落后于它守护的那份文档。mrrc_ft710 的注册表声明 sdd_version: V1.7，而设计文档在 v1.8.0。mrrc_modern 声明 V2.27，文档在 V2.30。mrrc_ft8 声明 V1.0，文档在 V1.8。三中三。执行仍然有效 —— 规则是基于模式的，路由索引实时解析 —— 但一个评审者会去信的那份版本元数据，在三个地方都是错的。

④ 然后是那个差点往反方向走的案例。三个看起来都很权威的来源一致说 FT-710 在 v1.8.0：最新的 git tag、设计文档的 quick-facts 表、以及产品自己的网站。我正准备把台账里的 v1.8.1「校正」下去跟它们对齐。然后我读了 CHANGELOG.md，那里有一条 [v1.8.1] — 2026-08-16。台账一直是对的，而且对在一个具体的地方：它记了两个字段，"Source: v1.8.1" 和 "Windows package: v1.8.0"，因为那是两个不同的工件处在两个不同的版本上。tag、文档和网站各自描述的都是已打包的发布版。只有台账保住了这个区分。

主张

在这里救场的是精确。单一的「版本」字段无论填哪个值都会是错的，而且会诱发我差点做出的那次修正。当两个工件可以处在不同版本上时，schema 就需要两个字段 —— 于是那个看起来像马虎的歧义，结果是唯一正确的记录。

还有第五条发现，它是对「我改了什么」的一个约束。有几个子站页面也提到 439 和 633。它们不是在竞争同一个论断。其中一处写的是 "v1.12.0 Windows Stable (V2.27) — published after 633/633 tests on macOS and Windows 11"，那是一份带日期的记录，记的是那个版本发布时为真的事。另一处是版本史的一行：SDD V2.30，日期 2026-08-29，作者字段是 Kimi。在这两处把 633 改成 682 并不会让它们变准确。会让它们变假 —— 变成声称某次发布通过了一套当时还不存在的测试。

事实

一份带日期的证据记录与一条当前状态声明是不同的工件，即便它们含同一个数字。本文相关的修正被限制在六个做出当前状态声明的门户文件内。任何仓库里的历史记录都没有被修改。

这就留下了一个台账自己回答不了的问题：谁来告诉台账？这一轮的答案是：一个人在一个周六跑了测试套然后注意到了。这不可扩展，而且它是整套系统里最清楚的一处剩余缺口 —— portal/tests/ 里的契约测试现在把本文引用的数字钉住了，所以至少这篇文章不可能相对普查悄悄漂移。台账本身仍然靠人的注意力。

从未被交出去的部分

上面这一切读起来可能像是在论证应该交出更多。不是。而这条边界是我最不希望被转述掉的部分。

Agent 承担执行。人保留三样：意图 —— 这项工作为何存在、什么算成功、什么是刻意排除在范围外的；边界 —— 架构裁决、安全不变量，以及 agent 不得为了一个通过的测试而交易掉的约束；判断 —— 现有证据够不够说一件事已完成、已发布、或已安全。对一次发射、一次发布或一条安全声明的责任，留在签署那份证据的具名的人身上。任何委托都不改变这一点。

四件事在任何 token 预算下都不可压缩：

  • 硬件。PCB 制板与台架 bring-up。EFHW 调谐器的 V3.0 设计与固件已完成，而它的声明停在设计目标，直到一块板子存在。
  • RF 安全。真实电台上的 PTT 通路与发射授权。服务端测试通过不为客户端签字。
  • 在用电台。在操作者自己的天线、波段条件与邻居上的现场验证。
  • 发布。发布决定，以及什么被标为已发布 —— 因为那个标签是对一个人的承诺。

而有一个已知缺陷是刻意保持打开的。FT710Mobile 这个 iOS 客户端有一个未解决的 P0 PTT 安全问题。439 项通过的服务端测试不能关闭它。另一个客户端通过也不能关闭它。它继续被列在已知问题里，而那个状态说的就是「我们不装」。

这就是为什么证据系统跑在两条被禁止交叉的阶梯上。

产品成熟度（A 阶梯）

  1. 设计目标
  2. 仿真结果
  3. 自动化测试
  4. 台架验证
  5. 现场验证
  6. 已发布／在运行
  7. 已延期／已知问题

过程约束（B 阶梯）

  1. B1 约束注册表条目
  2. B2 spec／plan 轨迹
  3. B3 会话内执行
  4. B4 拦截已验证

一个 B4 徽章永不提升 A 级声明。再多的约束条数也不会让一次台架结果变得不那么必要。EFHW 这一族在过程阶梯上处于 B2，在产品阶梯上处于设计目标，而这两个事实互不交易。

坚持这一点的原因是，另一种选择确实诱人。52 条机器可读约束、一次可复现的拦截、七十亿 token 的已验证工作 —— 很容易让这股势头暗示出超过它所能证明的东西。古典的表述比我的版本更锋利：知而不行，只是未知。一条不会拦的约束，等于你并不真的拥有这条约束。但反过来一样成立 —— 行也不等于知。一次被拦下的编辑证明门禁有效。它不证明天线匹配、不证明电台可以安全键控、不证明这次发布准备好了。

主张

这套 harness 的价值不在于它让 agent 做得更多。而在于它让剩下的人类工作变得可读：三项保留的问责、四道不可压缩的门禁、两条不能交叉的阶梯，以及一个公开保持打开的缺陷。把执行交出去只有在剩余部分小、有名字、且可强制执行时才划算。

如果你不做电台，什么可以迁移

这里没有一样东西需要业余无线电、Python 或某个特定模型供应商。可迁移的序列是七步，而诚实的读法是：第 1、2、6 步装着几乎全部价值。

  1. 在写代码之前，写下什么算成功

    不是愿景陈述 —— 是一个验收条件加一份显式的范围外清单。业务 harness 就是三个问题：这件事为何存在、服务谁、怎样才算完成。agent 极擅长优化一个目标，而对那个目标是否正确极其无动于衷。

  2. 让你的约束机器可读，每条都带引用

    severity、scope、patterns，加一个指回产生它的那次决策或那次事故的引用。一条没人能追溯的规则，会被第一个觉得它碍事的人删掉。三个仓库 52 条规则不算多；让它们起作用的是每条都说清了自己为什么存在。

  3. 在运行时加载契约，不是在入职时

    引用那份权威文档并实时切取。不要把它复制进一个某人会忘记更新的提示模板 —— 那份副本正是知识前去变成虚构的地方。

  4. 把门装在写入上，不是装在评审上

    一个在编辑落盘之前跑的检查不花什么钱，而且它能挡住事故。一个在之后跑的检查依赖有人去看。如果只能负担一个，买那个 hook。

  5. 把每一次事故变成同一次改动里的一条规则

    那次频漂 bug 成了 AD-014，成了 cat-no-dn，成了一次被拦下的编辑。三步，全都有记录，没有一步是可选的。一次只产出修复的事故，会在另一个文件里再发生一次。

  6. 把每一个数字与第二个来源对账

    我的第一次普查错了 16 亿 token，而同一块盘上就躺着一个持有正确答案的数据库。来源之间的不一致才是发现。你没有核对过的一致，不是佐证。

  7. 让两条阶梯分开，并把打开的缺陷公开

    过程证据与产品成熟度是关于同一份工作的两个不同论断。把它们压扁，就是一个工具优秀的项目最后告诉别人它已经完成了的方式。

要做粗略自评，机制卷里的成熟度阶梯是：1 Ad hoc，知识存在于个人动作与临时笔记；2 可重复，有了基本 harness 与执行路径；3 可追溯，规格、代码、测试、发布与证据能连起来；4 证据驱动，声明包含来源、环境、方法、结果与局限；5 可复用，已验证的架构与约束能跨产品迁移。

卷一里那六个月是第 1 级走向第 2 级。三个装了 guardian skill 的仓库在第 4 级，而共享本体加上被抽出来的后端抽象，是第 5 级的开端。文档体量与测试数本身不推进级别 —— 这句话写在机制页上，而且它是最值得相信的那一条。

推论

如果你只从这篇文章里采纳一件事，采纳第 6 步。它最便宜，不需要任何工具，而且是唯一能抓住「你用来为其余一切辩护的那些证据」里的错误的一步。其余所有东西都可以慢慢建。而「第二个来源是什么」这个习惯必须从第一天就在，因为正是这个习惯会告诉你第一天做错了。

方法及其局限

  • 归属依据是每个工具自己记录的工作目录。从父目录发起的会话落入「未归属」，故按仓库的表是下限。
  • 模型标识符是各 harness 自己记录的，这是事实。某个请求实际由哪家供应商服务则是推论：model_provider: api111 与 provider: mulerun 表明路由并非总是直连，而没有抓取任何流量去确认某个端点。
  • 只有这台机器的存储可用。在别处做的、或本地已被清理的工作是缺失的 —— 这也是为什么 Claude Code 的跨度比最老仓库晚三个月才开始。
  • 缓存重读的主导程度因 harness 与计价模型而异，故 95.2% 这个数字描述的是这些工具上的这一批工作负载，不是 agent 工作的通则。
  • 有一条工作区说明在这台机器上是坏的：文档里教的跨站搜索写法把目录赋给一个字符串变量再不加引号展开。在 zsh 下（它不对未加引号的展开做词分割），且 grep 实际解析为 ugrep，八个目录被当成一个不存在的路径传入 —— 退出状态 2，无输出，与「没有命中」无法区分。一次覆盖全部子站的静默假绿。数组写法可用，本文用的就是它。
