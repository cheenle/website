Intelligence · Field Distillation

One USB Cable.
Four Dimensions of Agentic Engineering.

This is not a story about how powerful AI is, nor a chronicle of seven repositories. It is four dimensions distilled from one real case — they explain everything that happened in this case, and they apply to your business. Case and data are demoted to evidence: every number has a source, every boundary is stated.

Data collected 2026-09-05. This article cross-verifies with the published Seven Billion Tokens, One Field Incident ("7B"): that one is the ledger; this one is the distillation. Where the two differ in caliber, the appendices state the difference item by item.

00 · Thesis

Separate judgment from execution

One sentence that explains everything the case contains.

Author's thesis

Agentic engineering is not "using AI to write code". It is separating judgment from execution: judgment settles into contracts, execution is delegated to agents, and evidence decides whether a contract lives or dies.

This one sentence explains why the same operator, from 2025-10 to 2026-04, spent an estimated ~230 million tokens (iFlow, 37,202 assistant turns, six model backends — usage fields all zero, estimated by character count, not recorded) and was left with nothing but evaporated chat logs, while from 2026-03 to 2026-09, 7.1 billion tokens left seven repositories, four product families, 52 machine-readable constraints, and a transferable method. The difference is not the model, not the prompts — it is whether judgment has a carrier that outlives the conversation.

What AI amplifies is the intent that has already been defined. An undefined intent gets its chaos amplified. The four dimensions below unfold that judgment.

Dimension I · Engineering History

The Abstraction Ladder Moves Up Again

Software engineering history is a history of delegation — and this rung delegates implementation itself.

01 · Argument

Each generation delegates one more layer of "how"

Machine code → assembly → high-level languages → frameworks → cloud services: every generation of tooling delegates a layer of "how to do it" to the machine, and humans move one rung up.

Author's thesis

Agentic is the next move up that ladder — it delegates the whole "implementation" layer. What remains for humans is exactly three things: define intent (what is wanted), draw boundaries (what must not happen), exercise judgment (does this count as done).

Inference

The bottleneck has moved. Once implementation can be delegated, the scarce resource is no longer "speed of writing code" but "the ability to state intent, boundaries and acceptance clearly". That is where the largest workload in this case sits — not in generation, in definition.

12 specs + 10 plans

Twelve design specs and ten implementation plans (docs/superpowers/ in the website repository) — each one a physical instance of "say it clearly first".

d4a7a32 · 2026-08-02

The ft8 repository's first substantive commit brought in — before any business code — an 84-line AGENTS.md, a 15-chapter SDD, a constraint registry and contract tests in one shot. The definition layer existed before the implementation layer. (Strictly this was ft8's third commit; the root commit c545d69 is a one-line README.)

2026-07-09 · acceptance first

The optimization plan of 2026-07-09 opens with acceptance conditions ("a user completes project selection within 10 seconds", "Lighthouse mobile LCP < 2.5s"); the implementation schedule comes second.

Intent must be stated in business language, and must hold without AI. None of the four intents in this case starts with "let's use AI": a universal remote station interface that does not rewrite CAT logic per radio (MRRC, 2026-03-06, ba66892); bypassing the desktop software to get synchronized control and transmit safety (sunsdr, 2026-06-21, 38cb85e); using the USB cable already on the desk instead of an SCU-LAN10 accessory for remote operation (mrrc_ft710, 2026-07-06, 9403e2e — the FT4222 bridge inside that cable yields real spectrum at roughly 21 fps plus 48 kHz bidirectional audio); modeling FT8's 15-second cycles, decode selection and controlled transmit as a complete workflow (ft8, 2026-08-03). Save money, save effort, safety, save time — if removing the word "AI" kills your business need, it was never a business need; it was a technology demo.

Dimension II · Epistemology

The Carrier Decides How Long Knowledge Lives

Upgrade the carrier once, and the half-life of knowledge grows by an order of magnitude.

02 · Argument

Three eras of carriers, all lived in one case

The effect of using AI depends not on model strength but on what carrier knowledge settles into.

Author's thesis

The carrier of knowledge determines the lifespan of knowledge. This case lived through all three eras in sequence.

EraCarrierFate of knowledgeCase evidence
Conversation erachat logsevaporates with the sessioniFlow: 37,202 turns, an estimated ~230 million tokens (usage fields all zero; estimate, not recorded) — output produced, zero sediment
Document eraSDD / practice guidesgoes stale, gets skippedMRRC's SDD framework (2026-05-02, 58aa675) and the FDE practice guide (2026-05-10, 88f519f)
Contract eramachine-readable constraints + runtime gatesneeds no remembering — appears when it shouldsdd-guardian (2026-07-20, 2498ec2): constraints injected at session start, violations intercepted by a PreToolUse hook before an edit lands on disk
Fact

52 constraints = 52 judgments made permanent. ft710 has 17, modern 21, ft8 14; each carries severity, scope, match pattern, and a citation to the decision or incident that produced it. They are not "remembered" — agents came and went (claude-code, pi, kimi, codex, mulerun, opencode) and not one constraint was lost, because the carrier lives in the repository, tool-agnostic.

Inference

This is the precondition for running many harnesses in parallel: the contract is tool-agnostic, so any harness loads the same contract on entry and carries no knowledge away on exit. It is also why the incident conversion rate — not the incident count — is the true measure of an organization's learning ability: how fast does an incident become permanent immunity?

FT-710 frequency drift · 13 days

Field fix (2026-07-07, 72fd6f0 — DN; is actually a VFO step command; polling it caused ~20 Hz drift per call) → design ruling AD-014 written into the SDD (07-08, bb128ff) → machine-readable constraint cat-no-dn (07-20, 2498ec2) → reproducible pre-edit interception (exit code 2). 13 days from stepping into the pit to the system never being able to step into it again.

Backup disk-full · 7 days

Server /var/tmp at 100% (2026-08-29, ~300 MB per backup; fix commit 7cfefec in mrrc_modern) → sister fix commits in four repositories on the same day (09-05) → and, following the thread, the hidden defect that "portal backups had never worked" (067f565 — an unquoted remote heredoc let the local shell expand variables early). 7 days, and the rules were promoted to the four deployment iron rules in CLAUDE.md.

Reproduced block in mrrc_ft710, 2026-09-05
$ python3 .agents/skills/sdd-guardian/harness/sdd_context.py check probe_b4_tmp.py
SDD-GUARDIAN: blocking violations found:
[BLOCK] cat-no-dn (AD-014; SDD V1.2 freq-drift incident) probe_b4_tmp.py:2: return c.query("DN;")
$ echo $?
2

Had the story stopped at "bug fixed", the next session, the next agent, the next product family would make the same mistake. The fix is only the first link; ruling → constraint → interception is what turns "a pit one person stepped into" into "a pit the system can never step into again".

Dimension III · Economics

Tokens Are the Price of Uncertainty

Read the meter not by its total, but by where it was spent.

03 · Argument

Fuel paid to eliminate uncertainty

Tokens are neither a productivity trophy nor waste — they are the unit of fuel spent on removing uncertainty.

Author's thesis

A token figure is read by where it was spent, not by how large it is. Four pieces of evidence follow.

Evidence 1 · density, not volume

Tokens do not follow lines of code; they follow uncertainty density. The ft8 repository: 1.88 billion tokens against ~70k source lines (about 26,800 tokens/line) — DSP, 15-second timing, transmit guards, every line high-risk. The wfview reference tree: 23.5 million tokens against ~170k lines (136 tokens/line) — reading reference only. A nearly 200× density difference measures not workload but "how much here we did not previously know".

Evidence 2 · peaks land on uncertainty

The project × week token series maps one-to-one onto business events: 360 M in W30 lands on ft710's vertical slice against unknown hardware behavior; 730 M in W33 lands on ft8's timing-safety push; 1.26 B across W34–35 lands on modern's platform abstraction — "which assumptions are model-specific" was the most expensive question; 720 M across W35–36 lands on website's expression-and-evidence rebuild.

Evidence 3 · the contract tax

Most of the spend is the tax of contracts not being machine-readable enough. 95.2% of recorded tokens are cache-read — the same context loaded again and again. This is not a rhetoric of waste; it is an optimizable metric: the more machine-readable and slice-loadable the contract, the less context each delegation must reload.

Evidence 4 · measurement obeys the same discipline

The first census was wrong by 1.6 billion (codex's cached_input_tokens is a subset of input_tokens and cannot be added; pi's totalTokens already contains everything) — another database on the same disk held the correction. And on the very day of data collection for this article (the day 7B was published), claude-code's line caliber was found to double-count chunks of the same API response: deduplicated by message.id, the actual figure is 1,175,403,254 tokens (7,519 API responses), not 3,207,496,620 — a 2.7× inflation.

Inference

The right way to lower token consumption is not to use less AI — it is to lower uncertainty itself. And a measurement boundary is not something checked once before publication; it is a discipline that stays in force. Dimension IV · Responsibility

Two Ledgers, and Three Things That Cannot Be Delegated

You can delegate the doing; you can never delegate the "does it count".

04 · Argument

An accounting system against self-deception

Delegation has an absolute boundary — and policing it takes two separate ledgers.

Author's thesis

You may delegate "doing"; you may not delegate "whether it counts". Preventing self-deception requires an accounting system — two ledgers that never vouch for each other.

Ledger A · Product maturity

  1. design target
  2. simulation
  3. automated test
  4. bench verified
  5. field verified
  6. released / operational
  7. known issue (the honest extra rung)

Ledger B · Process evidence

  1. B1 registry entry exists
  2. B2 spec / plan trail
  3. B3 enforced inside sessions
  4. B4 interception reproduced

The two ledgers never intersect: a B4 process badge never promotes an A-level product claim. "Our process is strict" and "our product works" are independent claims; evidence for the first cannot vouch for the second.

Fact

The delivery evidence actually executed on 2026-09-05 must be read under this discipline: FT-710 passes 439 tests, yet FT710Mobile's P0 PTT safety issue stays open — 439 server-side tests cannot close a client-side safety claim; modern's 682 tests carry one error, a Windows-only launcher failing to import on macOS — an environment limit, not a product defect; ft8's 937 is collected, not passed, and the wording must keep the distinction; the EFHW tuner firmware is complete, but until PCB fabrication and bench verification its claim status stays design-target — what is not on a board must not be described as existing.

Three things can never be delegated: hardware fabrication and bench bring-up; RF safety and live-station verification; the decision to release and the judgment of whether evidence is sufficient. They are non-delegable not because AI is not strong enough, but because responsibility cannot be delegated — the person who bears the consequences must have made the judgment personally. The inner loop (Specify → Implement → Test → Review) can be handed to agents wholesale; intent, boundaries and judgment stay human forever.

05 · Closing

Ask where it settles first

The four dimensions converge into one question.

Author's thesis

For anyone who wants to do business with AI: first ask "where does my judgment settle", then ask "what can AI do for me".

AI use without a settling ground is consumption — 37,202 turns of conversation can leave nothing behind. AI use with a settling ground is asset accumulation — every incident, every ruling, every constraint lowers the cost of the next delegation. The distance from the conversation era to the contract era is not a model generation gap; it is one AGENTS.md, one living SDD, and one hook that stops you before an edit lands on disk.

If you only take one checklist, each dimension contributes one discipline:

  1. Definition before implementation (engineering history)

    Acceptance conditions, non-goals and boundaries are written before the first line of business code. Intent is stated in business language and holds without AI.

  2. Every incident must become a rule (epistemology)

    The fix is only the first link; ruling → machine-readable constraint → pre-write interception closes the loop. Measure your incident conversion rate.

  3. Spend against uncertainty (economics)

    Where tokens go, uncertainty lives; reconcile every important number against a second source, and keep measurement discipline in force continuously.

  4. Keep the two ledgers apart (responsibility)

    Process evidence and product maturity never vouch for each other; "doing" can be delegated, "whether it counts" stays human forever.

Appendix D · Measurement Boundaries

Seven honesty statements

Every number in this article lives inside these boundaries.

  1. Tokens cannot be attributed to single commits

    Sessions span multiple commits, and commits do not record which session produced them. Every "commit × token" correspondence here is an aggregation at working-directory × time-window granularity — the finest grain that can be attributed.

  2. The claude-code dual caliber

    The line caliber (summing every jsonl line carrying usage) counts chunks of the same API response multiple times and inflates by about 2.7×; deduplication by message.id gives the actual API consumption. The published census used the line caliber; Appendix B lists both columns side by side. Other tools are unaffected.

  3. Retention bias

    claude-code local logs are retained only back to 2026-08-05; most early consumption by MRRC (from 03-06) and sunsdr (from 06-21) is missing, and sessions started from a parent directory cannot be attributed to a project. All figures are lower bounds.

  4. Turn calibers are inconsistent

    Each tool defines a "turn" differently (jsonl line / token_count event / user_message), so comparing turns across tools is meaningless — only tokens compare. codex's census turns=717 could not be reproduced; Appendix B uses token_count events instead.

  5. ft710 and modern share 149 commits

    modern forked from ft710's history and has been independent since 2026-08-17; summing the two repositories' commit counts double-counts that shared history, but tokens are attributed by working directory and are not double-counted.

  6. Commit classification is coarse

    Classification by message prefix (feat / fix / docs / …) files early free-form messages under "other"; the classification carries an error of about ±10%.

  7. Model identifiers are self-reported

    Model labels are facts as recorded by each harness; the actual API origin behind third-party routing (e.g. codex via api111, pi via mulerun) is inference, and is not claimed as fact.
