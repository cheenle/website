总纲抽象阶梯知识载体经济学责任收束边界

数据采集日期：2026-09-05。本文与已发布的《Seven Billion Tokens, One Field Incident》（下称《7B》）互证：那篇是账本，这篇是提炼。两篇数字口径如有差异，附录逐条说明。这是智能体工程方法的一次自述。

00 · 总纲

把判断从执行中分离

一句话，解释这个案例里发生的一切。

主张

Agentic 工程不是「用 AI 写代码」，而是把判断从执行中分离：判断沉淀为契约，执行委托给 agent，证据决定契约的存亡。

这一句话解释了为什么同一个操作者，在 2025 年 10 月到 2026 年 4 月用掉约 2.3 亿 tokens（iFlow，37,202 轮对话，六个模型后端；usage 字段全零，按字符估算、未记录）只留下蒸发的聊天记录，而在 2026 年 3 月到 9 月用 7.1B tokens 留下七个仓库、四个产品族、52 条机器可读约束和一套可迁移的方法。差别不在模型，不在提示词，在于判断有没有一个比对话更长寿的载体。

AI 放大的是「已被定义的意图」。未被定义的意图，放大的是混乱。下面四个维度，是这个判断的展开。

维度一 · 工程史

抽象阶梯的又一次上移

软件工程史是一部委托史——而这一代，委托出去的是「实现」本身。

01 · 论点

每一代工具把一层「怎么做」委托给机器

机器码 → 汇编 → 高级语言 → 框架 → 云服务：每一代工具委托一层「怎么做」，人上移一层。

主张

Agentic 是这一阶梯的再次上移——它把「实现」这一层整个委托出去。人剩下的只有三件事：定义意图（要什么）、划定边界（不能怎样）、行使裁决（算不算完成）。

推论

瓶颈转移了。当实现可以被委托，稀缺资源就不再是「写代码的速度」，而是「把意图、边界、验收说清楚的能力」。这正是这个案例里最大的工作量所在——不在生成，在定义。

12 份规格 + 10 份计划

12 份设计规格 + 10 份实施计划（website 仓 docs/superpowers/），每份都是「先把话说清楚」的实体。

d4a7a32 · 2026-08-02

ft8 仓库的第一个实质提交，在写下业务代码之前，一次性带入 84 行 AGENTS.md、15 章 SDD、约束注册表和契约测试——定义层先于实现层存在。（严格说这是 ft8 的第三个提交；根提交 c545d69 只有一行 README。）

2026-07-09 · 验收先行

2026-07-09 的优化方案开篇就写验收条件（「用户 10 秒内完成项目选择」「Lighthouse 移动端 LCP<2.5s」），实现排期反而在其次。

意图必须用业务语言表达，且不依赖 AI 也成立。这个案例里的四个意图没有一个以「用 AI」开头：一个通用的远程台站界面，不为每部电台重写 CAT 逻辑（MRRC，2026-03-06，ba66892）；绕开桌面软件拿到同步控制与发射安全（sunsdr，2026-06-21，38cb85e）；就用桌上这根 USB 线替代 SCU-LAN10 配件完成远程操控（mrrc_ft710，2026-07-06，9403e2e——这根线里的 FT4222 桥能给出约 21 fps 的真实频谱和 48 kHz 双向音频）；把 FT8 的 15 秒周期、解码选择、受控发射建模为完整工作流（ft8，2026-08-03）。省钱、省事、安全、省时——如果去掉 AI 这个词你的业务诉求就不成立，那它不是业务诉求，是技术 demo。

维度二 · 认识论

知识的载体决定知识的寿命

载体升级一次，知识的半衰期延长一个数量级。

02 · 论点

一个案例，完整经历三个时代

AI 使用的效果不取决于模型多强，取决于知识沉淀在什么载体上。

主张

知识的载体决定知识的寿命。这个案例按顺序完整经历了三个时代。

时代载体知识的命运案例证据
对话时代聊天记录随会话蒸发iFlow 37,202 轮、约 2.3 亿 tokens（usage 字段全零，按字符估算、未记录），有产出、零沉淀

事实

52 条约束 = 52 次判断的永生。ft710 17 条、modern 21 条、ft8 14 条，每条带严重级别、作用范围、匹配模式，以及指向产生它的那次决策或事故的引用。它们不是被「记住」的——agent 换了一个又一个（claude-code、pi、kimi、codex、mulerun、opencode），约束一条也没丢，因为载体在仓库里，与工具无关。

推论

这就是多 harness 并行成立的前提：契约与工具无关，所以任何 harness 进场都能加载同一份契约，出场也不带走任何知识。也因此，组织学习能力的真正度量不是「出了多少事故」，而是事故转化率——事故多快变成永久免疫。

维度三 · 经济学

token 是不确定性的价格

读懂它的方式不是看总量，是看它花在哪里。

03 · 论点

为消除不确定性支付的燃料

token 不是生产力奖杯，也不是浪费——它是为消除不确定性支付的燃料的计量单位。

主张

读懂 token 的方式不是看总量，是看它花在哪里。以下四条证据。

证据一 · 密度而非总量

token 不跟随代码行数，跟随不确定性密度。ft8 仓 18.8 亿 tokens 对应约 7 万行源码（约 26,800 tokens/行）——DSP、15 秒时序、发射守卫，每一行都高风险；wfview 参考树 2,350 万 tokens 对应约 17 万行（136 tokens/行）——只是阅读参照。相差近 200 倍的密度，测的不是工作量，是「这里有多少我们原本不知道的东西」。

证据二 · 峰值落在最不确定的时刻

项目 × 周的 token 时间序列与业务事件一一对应：W30 单周 3.6 亿落在 ft710 直连硬件行为不明的垂直切片期；W33 单周 7.3 亿落在 ft8 时序安全攻关期；W34–35 两周 12.6 亿落在 modern 平台抽象期——「哪些假设是型号特化的」这个问题最贵；W35–36 两周 7.2 亿落在 website 的表达与证据系统重建。

证据三 · 契约不够机器化的税

大部分消耗是「契约不够机器化」的税。已记录 token 中 95.2% 是 cache-read——同一份上下文被反复加载。这不是浪费的修辞，是一个可优化的指标：契约越机器化、越可切片加载，每次委托需要重载的上下文越少。

证据四 · 测量也服从证据纪律

第一次 census 错了 16 亿（codex 的 cached_input_tokens 是 input_tokens 的子集，不能相加；pi 的 totalTokens 已含全部，不能叠加其他字段）——修正它的是同一磁盘上的另一个数据库。而本文数据采集当天（即《7B》发表当天）又发现 claude-code 的行口径把同一 API 响应的分块重复计入：按 message.id 去重后实际为 1,175,403,254 tokens（7,519 次 API 响应）而非 3,207,496,620——行口径放大约 2.7 倍。

推论

降低 token 消耗的正确方式不是少用 AI，而是降低不确定性本身。测量边界也不是发表前检查一次的东西，是持续生效的纪律。附录 B 双口径并列，与已发表账本的差异逐条声明。

维度四 · 责任

两本账，与不可委托的三件事

可以委托「做」，不能委托「算不算」。

04 · 论点

一套防止自我欺骗的会计制度

委托有一个绝对边界，守住它靠两本分开的账。

主张

可以委托「做」，不能委托「算不算」。防止自我欺骗需要一套会计制度——两本永不相交的账。

A 账 · 产品成熟度

  1. 设计目标
  2. 仿真
  3. 自动化测试
  4. 台架验证
  5. 现场验证
  6. 发布运营
  7. 已知缺陷（诚实的一级）

B 账 · 过程证据

  1. B1 注册表有条目
  2. B2 有规格 / 计划轨迹
  3. B3 会话中被强制执行
  4. B4 拦截被复现验证

两本账不相交：B4 的过程徽章永远不会提升 A 级的产品声明。「我们的流程很严」和「我们的产品好用」是两个独立声明，前者的证据不能为后者背书。

事实

2026-09-05 当天实跑的交付证据必须按这个纪律读：FT-710 439 个测试全过，但 FT710Mobile 的 P0 PTT 安全问题仍然开放——439 个服务端测试不能关闭一个客户端安全声明；modern 682 个测试有 1 个 error，那是 Windows-only 启动器在 macOS 上的环境限制而非产品缺陷；ft8 的 937 是 collected 不是 passed，措辞必须区分；EFHW 调谐器固件完成，但 PCB 打样和台架验证之前，声明状态停在 design-target——板上没有的东西不许说成有。

三件事永远不可委托：硬件打样与台架调试、RF 安全与实台验证、发布与「证据是否充分」的裁决。它们不可委托不是因为 AI 不够强，而是责任不能委托——承担后果的人，必须亲自做过判断。内环（Specify → Implement → Test → Review）可以整个交给 agent；意图、边界、裁决永远在人手里。

05 · 收束

先问沉淀在哪里

四个维度收束成一个问题。

主张

送给想用 AI 做业务的人：先问「我的判断沉淀在哪里」，再问「AI 能帮我做什么」。

没有沉淀地的 AI 使用是消费——37,202 轮对话可以什么都不留下；有沉淀地的 AI 使用是资产积累——每一次事故、每一次裁决、每一条约束都在为下一次委托降低成本。对话时代到契约时代的距离，不是模型代差，是一个 AGENTS.md、一份活着的 SDD、一个会在编辑落盘前拦住你的钩子。

如果只要一张清单，四个维度各给一条纪律：

  1. 定义先于实现（工程史）

    验收条件、非目标、边界，写在第一行业务代码之前。意图用业务语言表达，不依赖 AI 也成立。

  2. 事故必须变成规则（认识论）

    修复只是第一环；裁决 → 机器可读约束 → 写前拦截才是闭环。度量你的事故转化率。

  3. 盯着不确定性花钱（经济学）

    token 花在哪儿，不确定性就在哪儿；每个重要数字双源对账，测量纪律持续生效。

  4. 两本账分开记（责任）

    过程证据与产品成熟度永不互相背书；「做」可以委托，「算不算」永远在人。

附录 D · 测量边界

七条诚实声明

本文每个数字都活在这些边界之内。

  1. token 不能精确归因到单次提交

    会话跨越多个提交，提交也不记录出自哪个会话。本文所有「提交 × token」对应都是工作目录 × 时间窗口级别的归集，这是可归因的最细粒度。

  2. claude-code 双口径

    行口径（每条带 usage 的 jsonl 行求和）把同一 API 响应的分块重复计入，放大约 2.7 倍；按 message.id 去重为实际 API 消耗。已发表 census 用行口径，附录 B 两列并列。其他工具无此问题。

  3. 留存偏差

    claude-code 本地日志仅留存至 2026-08-05，MRRC（03-06 起）与 sunsdr（06-21 起）的早期消耗大部分缺失；父目录发起的会话无法归属项目。所有数字都是下限。

  4. turns 口径不一致

    各工具对「一轮」的定义不同（jsonl 行 / token_count 事件 / user_message），横向比较 turns 没有意义，只有 tokens 可比；codex 的 census turns=717 未能复现，附录 B 改用 token_count 事件数。

  5. ft710 与 modern 共享 149 个提交

    modern 自 ft710 历史分叉，2026-08-17 起独立；两仓提交数合计时对这段共享历史有重复计算，但 token 按工作目录归属，不重复。

  6. 提交分类按 message 前缀粗分

    feat / fix / docs / … 的前缀分类把早期自由格式 message 归入 other，分类数有约 ±10% 的误差。

  7. 模型标识为 harness 自记事实

    模型标识是各 harness 自己记录的事实；经第三方路由（如 codex 经 api111、pi 经 mulerun）的实际 API 来源属推断，不作事实声明。
